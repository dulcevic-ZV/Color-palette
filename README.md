1) Práctica usada:
   Para este pequeño proyecto hice uso de Eslint. El cual es un linter para javascript que permite tener un código limpio y libre de errores.
   Al hacer uso de un linter tenemos a una especie de revisor que observa mientras se escribe el código, por lo cual, puede detectar algunos problemas, antes de ejecutarse, como:
   - Estilos de código inconsistentes
   - Código poco intuitivo y difícil de mantener
   - Errores de sintaxis
   - Malas prácticas
   También se realizó la Pull Request junto a una Code Review por parte de un compañero (como se puede observar en los colaboradores).

2) Qué problemas evita:
   Como mencioné con anterioridad, el uso de un linter permite que el código sea más limpio, intuitivo y fácil de mantener. Por ende, nos evita tener errores que no podamos observar
   durante la creación y que, al final, provoca que hayan problemas en tiempo de ejecución.
   Por otra parte, las pull request nos da la posibilidad de colaborar de forma efectiva y mantener una buena calidad en el código. Esto nos permite evitar inconsistencias antes de integrar
   cambios en el código.

3) Cómo se relaciona con lo discutido en clase:
   Por ejemplo, en el caso del Big Bag podemos observar que al hacer uso de las pull request tendremos una manera de colaborar eficazmente, evitando así errores en el código y haciendo las mejoras
   pertinentes pudiendo verificar los cambios antes de enviarlos al código.
   Además, al hacer uso de un linter podemos reducir nuestro trabajo, es decir, al llevar un código más coherente y limpio podremos evitar horas de limpieza de código y de resolver problemas que solo
   aparecieron una vez se ejecutó.
